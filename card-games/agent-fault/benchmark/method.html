BENCHMARK METHODOLOGY / 0.2.0

What this benchmark establishes — and what it does not

Evidence tier: Real external API response records when executed and exported. Human tabletop game quality is not inferred.

Experimental design

Eight scenarios × two preselected profile variations × two deck versions (v0.5-P and v0.5-T2) × four candidate Interference cards = 16 paired fixtures, 32 batched API calls, 128 candidate outputs. All 36 Interference cards receive coverage at least once per version, with some receiving twice. Pairing controls for scenario, agent profile, card ID and hidden Fault; the exact wording differs by version. Inputs are generated within GitHub Actions from frozen manifests.

What is held constant

Scenario identity, repetition, candidate IDs, personality and Fault ID. The hidden Fault and public Breakpoints are never included in the model request. The original and challenger Scenario wording can differ where the candidate revision changed the card. Calls are consecutive, not simultaneous, and model stochasticity remains uncontrolled.

Important limitations

Four candidate variations are batched into the same model request, so they are not independent agent runs. Responses are not necessarily isolated; model/provider updates may affect comparisons. The schedule is stratified for card coverage, not a random model of actual hands. Two samples per Scenario are insufficient to estimate precise win rates. In addition, a comparison may be confounded when both Scenario and Interference text change. No invented human ratings, laughter metrics or balance certifications are presented.

Adjudication

Qualified Breakpoint and Fault outcomes require the printed rules and source text; a human reviewer checks them after generation. Use the 30-word score limit. Mark valid/invalid and one or both Breakpoints, then the version's actual Fault condition. If any Breakpoint qualifies in a fixture, only those candidates remain eligible. Otherwise inspect Fault qualifiers. The Judge's subjective choice is not represented by a synthetic rating. Comedy ratings are notes for human review, not established audience response.

Security, billing and privacy

OpenAI API key is read by the Netlify function, never sent to browsers. Access token is sent with paid requests and saved in sessionStorage only; it does not appear in exported results. Trial outputs and annotations stay in browser localStorage until explicitly exported. API usage is billed to the account whose key was configured. Netlify may record standard function invocation logs, and OpenAI handles inputs under applicable API data-processing terms. Keep site visitor access restricted where practical; the token is the chargeable endpoint's security boundary on a public site.

Reliability notes

Each paid request is started only by the user; no automatic benchmark runs on page load. Batch start requests explicit confirmation. A failed request stops the batch rather than blindly retrying. Results are checkpointed after each successful response; importing a saved JSON file restores them. A single generation request may omit a candidate; missing labels remain flagged rather than silently imputed. API latency and usage metrics are recorded. Estimated pricing is intentionally omitted because model rates can change.

Further validation

Independent per-candidate conversations, multiple runs across model providers, blinded adjudication, and observed four-, six-, and eight-player tabletop sessions are necessary before declaring cards balanced or game ready.

GitHub Actions execution

Paid trials are run manually through GitHub Actions and require an OPENAI_API_KEY GitHub Actions repository secret. No API key or access token is needed in the GitHub Pages interface. The exported JSON artifact is stored temporarily in the workflow run and is imported into the browser for manual review.

The site is publicly hosted. Card text and fixture definitions are public. Trial outputs stay in the workflow artifact and your browser unless you export/share them.
